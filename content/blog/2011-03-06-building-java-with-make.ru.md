Каждый Java-проект, который мне попадается, приходит с `build.xml`, и каждый `build.xml` — это несколько сотен строк XML, делающих то, что для любого другого языка на машине делает Makefile в пятнадцать строк. Я собираю свою Java через `make`. Вот как, и вот честный отчёт о том, что вы при этом выигрываете и чем жертвуете.

## Makefile

Структура обычная: исходники в `src/`, скомпилированные классы в `build/`, а на выходе — один jar.

```makefile
JAVAC := javac
JAR := jar
JAVAC_FLAGS := -Xlint:all -encoding UTF-8

SRC_DIR := src
BUILD_DIR := build
JAR_FILE := myapp.jar
MAIN_CLASS := com.example.Main

SOURCES := $(shell find $(SRC_DIR) -name '*.java')
CLASSES := $(patsubst $(SRC_DIR)/%.java,$(BUILD_DIR)/%.class,$(SOURCES))

.PHONY: all clean run

all: $(JAR_FILE)

$(BUILD_DIR)/%.class: $(SRC_DIR)/%.java
	@mkdir -p $(BUILD_DIR)
	$(JAVAC) $(JAVAC_FLAGS) -d $(BUILD_DIR) -cp $(BUILD_DIR):$(SRC_DIR) $<

$(JAR_FILE): $(CLASSES)
	$(JAR) cfe $@ $(MAIN_CLASS) -C $(BUILD_DIR) .

run: $(JAR_FILE)
	java -jar $(JAR_FILE)

clean:
	rm -rf $(BUILD_DIR) $(JAR_FILE)
```

Шаблонное правило сопоставляет каждому исходнику его class-файл, так что `make` компилирует только изменившиеся исходники. Аргумент `-cp` включает и каталог сборки (для уже скомпилированных классов), и каталог исходников (чтобы `javac` мог найти исходники ещё не скомпилированных классов). Правило для jar с помощью `-e` задаёт в манифесте точку входа, так что результат запускается через `java -jar`.

Если у вас есть сторонние jar-файлы, положите их в `lib/` и добавьте в classpath:

```makefile
LIBS := $(wildcard lib/*.jar)
CLASSPATH := $(BUILD_DIR):$(SRC_DIR):$(subst $(eval) ,:,$(LIBS))
```

и используйте `-cp $(CLASSPATH)` в правиле компиляции.

## Что вы выигрываете

**Один инструмент для всего.** Проект редко состоит только из Java. Есть библиотека на C с обёрткой JNI, скрипт на Python, генерирующий исходный файл, руководство на LaTeX, shell-скрипт, упаковывающий релиз. Ant знает про Java. `make` знает про файлы и команды, а всё перечисленное — именно они. Одна и та же команда `make all` собирает всё дерево, а зависимости между Java-частью и остальным выражаются на том же языке, что и зависимости внутри каждой части.

**Настоящие зависимости.** Makefile — это граф зависимостей и ничего больше. Цели Ant — это список шагов для выполнения; его представление о том, что актуально, — это то, что реализовала каждая конкретная задача, и ответ задачи `javac` — сравнить метки времени исходников и классов для переданных ей файлов. `make` делает то же сравнение, но делает его для каждого правила, включая правила, которые вы написали для генерируемых исходников и для упаковки, единообразно, и позволяет сказать, что jar зависит от шаблона манифеста, а шаблон манифеста — от файла с версией.

**Никакого XML.** Это не эстетическая претензия. Описание сборки — это код, а XML — плохой язык для кода: многословный, неудобный для сравнения изменений и неспособный ничего вычислить без перехода в плагин. В Makefile есть переменные, функции, шаблонные правила и shell.

**Он уже есть.** На каждой Unix-машине есть `make`. Никому не нужно ставить инструмент сборки, чтобы собрать проект.

## Чем вы жертвуете

**Инкрементальная компиляция — не то, чем кажется.** Шаблонное правило перекомпилирует изменённый исходник, но классы Java зависят от других классов так, как файловая система этого не показывает. Измените константу в `A.java` — и `B.class`, который встроил эту константу, теперь неверен, а `make` об этом понятия не имеет, потому что `B.java` не менялся. У Ant точно такая же проблема, и он скрывает её точно так же плохо. Честное исправление в обоих случаях — `make clean` перед релизной сборкой и `javac` на всём наборе исходников при любом изменении, затрагивающем интерфейсы. Для проекта обычного размера полная компиляция занимает секунды, так что инкрементальное правило — удобство во время разработки, а не то, чему стоит доверять.

**Работа с classpath — ручная.** Элементы `<path>` и `<fileset>` в Ant, а позже Ivy и Maven управляют наборами jar за вас. С `make` вы перечисляете их сами, как выше, и сами разрешаете их зависимости. Для проекта с тремя jar в `lib/` это тривиально. Для проекта с сорока транзитивными зависимостями это реальная цена, и это самый сильный довод в пользу специфичных для Java инструментов.

**Java-разработчики этого не ждут.** Участник, который откроет проект и не найдёт ни `build.xml`, ни `pom.xml`, на минуту растеряется. Это всего минута, и Makefile достаточно короток, чтобы его за эту минуту прочесть, но это реальное трение, и я не делаю вид, будто его нет.

## К чему я прихожу

Для проекта, который почти целиком на Java и имеет большое дерево зависимостей, используйте инструмент, которого хочет это дерево зависимостей. Для всего остального, и особенно для всего, что смешивает Java с другими языками, Makefile проще, честнее показывает, что от чего зависит, и не добавляет систему сборки в список того, что новый участник должен выучить. Эти пятнадцать строк годами собирали каждую написанную мною программу на Java, и я ни разу не соскучился по XML.
