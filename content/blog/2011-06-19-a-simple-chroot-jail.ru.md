Иногда нужно запустить одну программу в «коробке», чтобы в случае взлома она не увидела остальную файловую систему. Самый старый инструмент для этого в Unix — `chroot`, который меняет то, что процесс считает корневым каталогом. Это не контейнер и не граница безопасности против решительного атакующего с правами root, но чтобы запереть сервис в маленьком собственном мирке, он прост и работает. Вот как собрать такую тюрьму вручную; сделать это стоит хотя бы раз, чтобы понимать, что за вас делают более изощрённые инструменты.

## Выбираем корень и находим зависимости

Допустим, программа — `/usr/bin/myapp`. Тюрьма — это просто каталог, который станет её `/`:

```bash
sudo mkdir -p /jail/{bin,lib,lib64,etc,dev,usr/bin}
```

Без разделяемых библиотек, с которыми она скомпонована, программа не запустится. Спросите у динамического компоновщика, что это за библиотеки:

```bash
ldd /usr/bin/myapp
```

Он выведет каждую библиотеку и путь к ней. Скопируйте в тюрьму бинарник и все названные библиотеки, сохранив прежние пути:

```bash
sudo cp /usr/bin/myapp /jail/usr/bin/
for lib in $(ldd /usr/bin/myapp | grep -o '/[^ ]*'); do
    sudo cp --parents "$lib" /jail/
done
```

`cp --parents` воссоздаёт структуру каталогов внутри `/jail`, так что библиотека из `/lib/x86_64-linux-gnu/` оказывается на соответствующем месте внутри тюрьмы. В этом весь фокус: программа в тюрьме ищет свои библиотеки по тем же путям, а теперь эти пути существуют внутри коробки.

## Оболочка, чтобы осмотреться

Пока вы настраиваете тюрьму, внутри нужна оболочка для проверок. Обычная оболочка вроде bash тянет за собой много библиотек. `sash`, автономная оболочка, собрана статически и содержит основные команды внутри себя, поэтому ей ничего снаружи не нужно:

```bash
sudo apt-get install sash
sudo cp /bin/sash /jail/bin/
```

Теперь можно войти в тюрьму и проверить, что мир программы полон:

```bash
sudo chroot /jail /bin/sash
```

Если команда внутри жалуется, что файла нет, значит, это зависимость, которую вы ещё не скопировали.

## Файлы устройств

Многим программам нужен как минимум `/dev/null`, а некоторым ещё `/dev/zero` и `/dev/urandom`. Это не обычные файлы; создайте их заново с помощью `mknod`:

```bash
sudo mknod -m 666 /jail/dev/null c 1 3
sudo mknod -m 666 /jail/dev/zero c 1 5
sudo mknod -m 644 /jail/dev/urandom c 1 9
```

Числа — это старший и младший номера символьных устройств, те же, что использует настоящий `/dev`.

## Запускаем программу в тюрьме

```bash
sudo chroot /jail /usr/bin/myapp
```

Теперь процесс видит `/jail` как свой корень. Он не может открыть `/etc/passwd` хоста, не может прочитать ваш домашний каталог, не может бродить по файловой системе, потому что изнутри всего этого не существует.

## Чем chroot не является

Будем честны насчёт ограничений, потому что chroot часто доверяют больше, чем он может дать.

- **Процесс, запущенный от root, может вырваться из chroot.** Это способ ограничения, уменьшающий случайную экспозицию и сдерживающий непривилегированный сервис, а не песочница против атакующего с правами root. Запускайте программу в тюрьме от непривилегированного пользователя.
- Он делит с хостом ядро, сеть и таблицу процессов. Он скрывает файловую систему и больше ничего.
- Поддерживать скопированные библиотеки в актуальном состоянии придётся вам. Исправление безопасности в библиотеке на хосте не дойдёт до копии внутри тюрьмы, пока вы не скопируете её снова.

Именно поэтому существуют контейнеры: они добавляют пространства имён для сети, процессов и пользователей, а также инструмент, который управляет файловой системой за вас, поверх той же самой идеи. Соберите chroot один раз вручную, и ценность контейнера станет очевидной, потому что вы на себе прочувствуете каждую брешь, которую он закрывает.
