Рано или поздно веб-приложению приходится хранить файлы: загруженные пользователями изображения, PDF, вложения. Положить их можно в два места — в файловую систему или в базу данных, и к базе данных тянутся те, кому хочется держать всё в одном месте, резервировать одной командой и защищать одним набором прав. Для этого в MySQL есть тип `BLOB`. Ниже — как правильно отдавать из него файл, а затем довод в пользу того, чтобы этого не делать.

## Таблица

```sql
CREATE TABLE files (
    id        INT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
    name      VARCHAR(255) NOT NULL,
    mime      VARCHAR(127) NOT NULL,
    size      INT UNSIGNED NOT NULL,
    modified  DATETIME NOT NULL,
    data      LONGBLOB NOT NULL
);
```

Храните MIME-тип и размер рядом с байтами. Вычислять их в момент отдачи можно, но расточительно, а размер нужен для заголовка ещё до того, как данные прочитаны. `LONGBLOB` вмещает до четырёх гигабайт; просто `BLOB` останавливается на 64 килобайтах — это первый сюрприз, на который натыкаются все.

## Скрипт

```php
<?php
$id = isset($_GET['id']) ? (int) $_GET['id'] : 0;
if ($id <= 0) {
    header('HTTP/1.1 404 Not Found');
    exit;
}

$db = new PDO('mysql:host=localhost;dbname=site;charset=utf8', 'user', 'password');
$db->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);

$stmt = $db->prepare('SELECT name, mime, size, modified, data FROM files WHERE id = ?');
$stmt->execute(array($id));
$row = $stmt->fetch(PDO::FETCH_ASSOC);
if (!$row) {
    header('HTTP/1.1 404 Not Found');
    exit;
}

$etag     = '"' . md5($id . $row['modified'] . $row['size']) . '"';
$modified = gmdate('D, d M Y H:i:s', strtotime($row['modified'])) . ' GMT';

if ((isset($_SERVER['HTTP_IF_NONE_MATCH']) && $_SERVER['HTTP_IF_NONE_MATCH'] === $etag) ||
    (isset($_SERVER['HTTP_IF_MODIFIED_SINCE']) && $_SERVER['HTTP_IF_MODIFIED_SINCE'] === $modified)) {
    header('HTTP/1.1 304 Not Modified');
    exit;
}

header('Content-Type: ' . $row['mime']);
header('Content-Length: ' . $row['size']);
header('Content-Disposition: inline; filename="' . addslashes($row['name']) . '"');
header('Last-Modified: ' . $modified);
header('ETag: ' . $etag);
header('Cache-Control: public, max-age=86400');
echo $row['data'];
```

В этом скрипте важны четыре вещи, которые обычно упускают.

**Приводите id к числу.** `(int)` превращает всё враждебное в строке запроса в число. Подготовленный запрос вас бы и так защитил, но запрос `id=abc` должен давать 404, а не обращение к базе.

**Отправляйте настоящий тип содержимого.** Без него браузер гадает, и для PDF его догадка оборачивается то диалогом загрузки, то экраном мусора. Тип был записан при загрузке — используйте его.

**Отправляйте длину.** Браузеры показывают прогресс и могут повторно использовать соединение, только когда знают, сколько данных придёт. Размер у вас есть в таблице; незачем заставлять их ждать закрытия соединения.

**Поддерживайте условные запросы.** Файлы — самое кешируемое из всего, что отдаёт сайт. Если выдавать `Last-Modified` и `ETag` и отвечать на повторный запрос кодом `304`, второй просмотр обойдётся одним маленьким запросом, а не новой перекачкой всего BLOB из базы данных.

Обратите внимание и на то, чего в скрипте нет: ни `ob_start()`, ни вывода перед заголовками, ни закрывающего тега `?>`, из-за которого после байтов рискует уйти лишний перевод строки.

## Почему файловая система обычно лучше

Теперь довод против. Всё сказанное выше работает, и я запускал это в продакшене. И всё же в большинстве случаев это неправильная архитектура.

Файл из базы данных, прежде чем дойти до клиента, проходит через память базы данных, сетевой протокол, память PHP и веб-сервер. Файл на диске передаётся ядру через `sendfile()` веб-сервером, который десятилетие оптимизировали именно под это, и PHP вообще не вызывается. Для всего, что крупнее миниатюры, разница не в нескольких процентах: это разница между сайтом, который отдаёт картинки, и сайтом, чья база данных занята отдачей картинок.

Резервное копирование становится не лучше, а хуже. Дамп базы данных с гигабайтами BLOB-ов соответственно дольше создаётся, передаётся и восстанавливается, а восстановление небольших важных данных теперь тащит за собой большие и неважные. Репликация доставляет каждый байт каждой загрузки на каждую реплику.

И эксплуатационные инструменты тут не подходят. Столбец с BLOB-ами нельзя ни `ls`, ни `rsync`, ни отдать каталогом CDN.

Правильный шаблон — тот, к которому в итоге пришла каждая большая система: **храните байты на диске под именем, выведенным из записи, а в базе данных — только метаданные.** Таблица выше теряет столбец `data` и получает `path`. Скрипт выше превращается в проверку прав, за которой следует `X-Sendfile` или перенаправление. Всё остальное, включая заголовки кеширования, остаётся прежним.

Оставьте подход с BLOB для случаев, которым он действительно подходит: для крошечных файлов, для файлов, которые должны меняться в одной транзакции со своей строкой, или для развёртывания, где у вас и правда один процесс и файловой системы, о которой стоило бы говорить, нет. В остальных случаях база данных — для данных о файлах, а диск — для самих файлов.
