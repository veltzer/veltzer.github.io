`.htaccess`, который WordPress пишет для себя, исходит из того, что на домене больше ничего нет. Каждый запрос, не совпадающий с существующим файлом, передаётся `index.php`, и WordPress решает, что он означает. Если ваш сайт — это ещё и фотогалерея, несколько статических страниц, пара собственноручно написанных скриптов и блог, это допущение ошибочно, а симптомы странные: опечатка в URL галереи выдаёт страницу WordPress «не найдено» в оформлении блога, а каталог, который вы собирались защитить, отвечает записью из блога. Вот файл, которым я пользуюсь вместо этого, блок за блоком.

## Какую структуру он предполагает

```text
/var/www/site/            document root
    .htaccess             this file
    index.html            the front page, static
    gallery/              a photo gallery, its own application
    scripts/              my own PHP scripts
    blog/                 WordPress, installed in a subdirectory
    blog/.htaccess        WordPress's own file, left alone
```

Смысл такой структуры в том, что WordPress живёт в `blog/`, а его правила — в `blog/.htaccess`, где они могут влиять только на URL под `/blog/`. Всё остальное обрабатывает корневой файл.

## Корневой файл

```apache
# Nothing in this file mentions WordPress. That is deliberate.

Options -Indexes
ServerSignature Off

# Deny access to files that should never be served.
<FilesMatch "^(\.htaccess|\.htpasswd|\.git.*|.*\.(bak|old|sql|log))$">
    Order allow,deny
    Deny from all
</FilesMatch>

# The blog moved from the root to /blog/ in 2010; keep the old links alive.
RewriteEngine On
RewriteRule ^([0-9]{4})/([0-9]{2})/(.*)$ /blog/$1/$2/$3 [R=301,L]
RewriteRule ^feed/?$ /blog/feed/ [R=301,L]

# Protect the scripts directory with a password.
<IfModule mod_auth.c>
</IfModule>

# Sensible defaults for static content.
<IfModule mod_expires.c>
    ExpiresActive On
    ExpiresByType image/jpeg "access plus 1 month"
    ExpiresByType image/png "access plus 1 month"
    ExpiresByType text/css "access plus 1 week"
</IfModule>

AddDefaultCharset UTF-8
```

## Блок за блоком

**Никаких листингов каталогов, никакого баннера с версией.** `Options -Indexes` не даёт Apache показывать содержимое каталога без индексного файла, а на смешанном сайте таких большинство. `ServerSignature Off` убирает версию Apache со страниц ошибок. Ни то ни другое не имеет отношения к WordPress, и в этом весь смысл: они действуют на весь сайт, значит, их место в корне.

**Файлы, которые никогда не должны отдаваться.** Редакторы оставляют после себя файлы `.bak`, дампы базы данных забывают в корне сайта, а каталог `.git` в корне — это полная копия исходников с историей для любого, кто её попросит. Блок `FilesMatch` запрещает их все, где бы они ни лежали. Собственный файл WordPress не делает этого для каталогов вне `blog/`, потому что не знает об их существовании.

**Перенаправления для старых URL.** Когда блог лежал в корне, его записи жили по адресам вида `/2009/07/some-title/`. Эти ссылки есть на чужих страницах и в поисковиках, а URL, который когда-то работал, должен работать и дальше. Два правила перезаписи постоянным перенаправлением отправляют старые адреса на их новое место под `/blog/`. Это единственное место, где корневой файл знает о существовании блога, и знает он только то, куда блог переехал.

**Каталог скриптов.** Пустой блок `mod_auth` — заглушка: собственно защита паролем живёт в `scripts/.htaccess`, где и место для `Require valid-user` и `AuthUserFile`, лежащего вне корня сайта. Я держу заглушку здесь, чтобы всякий, кто читает корневой файл, видел, что каталог где-то защищён.

**Кэширование и кодировка.** Долгий срок жизни для картинок, неделя для таблиц стилей и кодировка по умолчанию, чтобы простой текстовый файл с ивритом не показывался мусором. Опять-таки это для всего сайта, значит, в корень.

## Чего здесь нет — намеренно

Здесь нет `RewriteRule . /index.php`. Именно эта строка делает WordPress владельцем каждого неизвестного URL, и она остаётся в `blog/.htaccess`, где её написал WordPress и где она ловит только URL под `/blog/`. Опечатка в URL галереи теперь получает собственный 404 от Apache, как и должно быть, а запрос к `/scripts/` получает запрос пароля вместо записи в блоге.

Нет здесь и ничего, что трогает настройки PHP. Они относятся к конкретному приложению и должны лежать рядом с ним; поднять лимит загрузки для блога — [отдельное упражнение](@/blog/2011-02-20-increasing-wordpress-upload-size.md) со своим файлом.

## Почему это важно не только ради порядка

Правило перезаписи, которое ловит всё, — это решение о безопасности не в меньшей степени, чем о маршрутизации. Каждый запрос, на который не отвечают другие ваши приложения, становится запросом, на который отвечает WordPress, — с поверхностью атаки WordPress, выполняя код WordPress, в каталоге, который вы, возможно, защищали в расчёте на то, что до него доходят только URL блога. Ограничение правил подкаталогом означает, что уязвимость каждого приложения — это уязвимость его собственных URL, и не более того. Я уже писал о том, [как запереть сам каталог WordPress](@/blog/2010-06-26-wordpress-and-unix-security.md); это внешний слой той же идеи.
